# dsh-dispatch

给 DeepSeek Harness 加两个工具，把「很多次模型往返」压成「一次往返」。单步往返的固定成本（本机实测 TTFT 中位 3.0s、整步中位 5.7s）是这里唯一要消灭的东西。

| 工具 | 解决什么 | 代价 |
| --- | --- | --- |
| `run_tools` | 一次模型往返里执行多个工具调用（读 3 个文件、跑 2 条命令、抓 4 个网页），默认并发，可用 `after`（下标或 label）表达依赖 | 这一步的模型输出变长（要写 N 组参数） |
| `run_parallel` | 一次往返把 N 个互不依赖的子任务派给 N 个子 agent 真并行 | 子 agent 各自烧 token |

工具名固定为 `run_tools` / `run_parallel`；插件在 profile 级挂载，该 profile 下的每个会话都能用。

---

## 零、让模型自己想到用（系统提示词）

插件除了注册两个工具，还在 profile 级注册一段全局系统提示（`dispatch-policy`，约 8 行）：

> 发工具调用前扫一眼：这一批里有没有两个以上互不依赖的动作？有就合并成一次 `run_tools`，没有就直接发。多个独立重任务 → `run_parallel`。只有一步、或后一步要看前一步结果 → 不要硬包。判定只看一眼，不要为此展开推理。

覆盖范围：`standard` / `ptc` / `cordis`（创造模式）都会带上；`ptc` 下额外写明「在程序里写 `await tools.run_tools({steps:[...]})`」。唯一例外是 `minimal` 预设——它的 persona 声明了 `complete: true`，按内核规则会覆盖其它所有段，那段提示不会出现（工具本身仍然可用）。

不想要这段提示：把 patch 里的 `dsh-dispatch` 条目删掉，工具和提示一起消失。

## 一、它是怎么加速的

### 1. 一次往返里到底在等什么

一个 step 的墙钟 ≈ **首字延迟（TTFT）** + **生成输出 token** + **工具执行**。

本机实测（同一台机器、同一模型、20 个会话 982 个 step）：

| 分量 | 数值 | 占单步 |
| --- | --- | --- |
| TTFT（等到第一个 token） | p50 **3.0s** / p90 4.3s | 约 36% |
| 生成（含思考） | 输出 p50 611 tok ÷ 195 tok/s ≈ 3.1s | 约 45% |
| 工具执行 | p50 **0.56s** | 约 19% |

TTFT 与上下文长度几乎无关（36k 上下文 1,988ms、105k 上下文 2,346ms），所以它是一笔**按次数收的固定费**，不是「上下文太长拖慢的」。

### 2. 分开做 vs 合批：公式

```
分开做（N 个动作）≈ N × (TTFT + 生成 + 单个工具)
合批（一次 run_tools）≈ 1 × (TTFT + 生成(N 组参数) + max(工具))   ← 工具默认并发
```

省下来的是两块：

- **N−1 次 TTFT**：每少一次往返就少等一次首字；
- **工具串行改并发**：`sum(工具)` 变成 `max(工具)`。

代价是这一轮模型要多写 N 组参数（输出 token 变多），以及**单步超时必须够长**（默认 60s，`stepTimeoutMs` 可调）。

### 3. 为什么必须由插件来做

一次模型输出里能带几个 `tool_call` 由模型决定，执行侧改不了；但**内核原本还会把独占工具逐个串行执行**（`dsh` 的 `batch.js` 对非并发安全工具分组长度为 1）。本插件在工具内部拿到 `ctx.tools.execute`，把 N 个调用重新派发成并发 —— 这是「一次往返里真的让多个动作同时跑」的关键，纯提示词做不到。

### 4. 什么时候会自动停下

`dsh_browser_*`、`ask_user_question`、`todo_write` 会改动共享状态（同一个页面、同一个人、同一份待办），所以它们**恒定独占**：等批内其他调用跑完再上，自己跑完才放行下一个。

## 二、什么情况下快多少

### 工具侧（实测，本机，`pwsh` 每条 `Start-Sleep 1`）

| 形状 | 串行本应 | 实测 | 说明 |
| --- | --- | --- | --- |
| 4 条独立命令 | ~4.0s | **1,315ms** | 默认并发 |
| 8 条独立命令 | ~8.0s | **1,451ms** | 默认上限 8 |
| 8 条 + `maxParallel: 4` | ~8.0s | **2,608ms** | 分两波 |
| 3 条 `after` 链 | ~3.0s | **3,777ms** | 依赖链不省工具时间 |
| 6 个快工具（read/grep/glob） | ~0.9s | **186ms** | 并发后只剩最慢那个 |

### 端到端（模型往返 + 工具）

| 场景 | 分开做 | 一次 `run_tools` | 提速 |
| --- | --- | --- | --- |
| 3 条各 2 秒的命令 | 30.4s（3 次往返） | **4.1s**（1 次） | **7.4×** |
| 4 条各 1 秒的命令 | 19.9s（4 次往返，实测 5.98+4.66+4.66+4.56s） | **约 5.7s**（1 次往返：工具 1.3s + 单步 4.4s） | **3.5×** |
| 4 个文件读（工具很快） | 13.2s（4 次往返） | **8.15s**（1 次） | 1.6× |

「分开做」的端到端取自会话日志的 `step/start` → `step/end` 累加；「合批」的单步模型时间取同类低输出步（同一会话、输出 <200 tok），避免拿「我恰好在写长文的那一步」当基线。

两者的差距说明一件事：**工具越慢、动作越多，收益越大**。读文件这类毫秒级动作，省下来的几乎全是往返；而每次往返本身还有 3s 首字 + 一段思考，所以 N=4 时只有 1.6×。

### 每动作的模型时间（本机 5,953 个历史 step）

| 每步承载的动作数 | 单步均值 | 折算每动作 |
| --- | --- | --- |
| 1 个 | 8.8s | **8.8s** |
| ≥2 个 | 12.4s | **6.2s** |

即：合批把每次动作的模型开销从 8.8s 压到 6.2s（−30%），因为固定成本被摊薄了。

---

### 5 动作小任务上的实测（同一窗口，同一模型，2026-11-11）

任务：`node -v`、`git --version`、读文件前 5 行、取一个 GitHub API 字段、写文件后读回。5 个子 agent，3 个「尽量合批」、2 个「严格串行」。

| 组 | steps | 工具调用 | run_tools | 模型时间 | 工具时间 | 墙钟 | 输出 tok |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 合批 ×3 | 4 / 5 / 5 | 4 / 5 / 5 | 0 / 1 / 1 | 57.3 / 34.7 / 51.8s | 1.0 / 1.6 / 1.3s | 58.8 / 37.2 / 53.8s | 2.5 / 2.9 / 2.9k |
| 串行 ×2 | 7 / 10 | 7 / 9 | 0 / 0 | 36.8 / 98.4s | 1.0 / 1.0s | 38.9 / 100.8s | 3.0 / 2.0k |

结论：步数 4.7 → 8.5（−45%），模型时间 47.9s → 67.6s（−29%），墙钟 49.9s → 69.9s（−29%）；但只有 5 个样本、单步方差 ±20s——串行的 s1（38.9s）比最快的合批样本（37.2s）只慢 1.7s，所以这个差距的置信度有限。工具时间只占墙钟 2–3%，合批省的是往返次数，不是「跑工具的时间」；慢工具任务才是主场：8 条 1 秒命令，串行 ≈8s，合批 1,451ms。
### PTC 模式下的实测（同一台机器，2026-11-11，全部在 PTC 会话里跑）

| 场景（都是 1 个 `run_code` 步） | 写法 | 程序耗时 | 整轮墙钟 |
| --- | --- | --- | --- |
| 3×`pwsh` 各 6s | `Promise.all` | 20,303 ms | 40.8s |
| 3×`pwsh` 各 6s | 逐个 `await` | 19,599 ms | 37.6s |
| 3×`web_fetch` | `Promise.all` | **966 ms** | 17.0s |
| 3×`web_fetch` | 逐个 `await` | 2,793 ms | 21.4s |
| 3×`pwsh` 各 6s（standard 预设，`run_tools`） | 默认并发 | **6,284 ms** | — |

结论：`pwsh` / 浏览器是独占工具，PTC 内核让同批独占调用构成屏障，`Promise.all` 只能拿到「排队」，拿不到重叠；`read` / `grep` / `web_fetch` 这类并发安全工具才是 `Promise.all` 的主场（966 vs 2,793 ms，2.9×）。另外在 PTC 里 `tools.run_tools` 看不到原生工具（返回 `UNKNOWN_TOOL: only run_code is callable directly`），所以要让 PTC 里的独占工具真正并发，必须把它们包进 `await tools.run_tools({steps:[...]})`：v0.2.8 起 `run_tools` 在程序内用 `parent` 令牌直派到执行器的 pipeline，绕开程序内那个「独占工具排队」的调度器。实测同一段 3×`pwsh`（各 6s）：`Promise.all` ≈ 19,600–20,300 ms，`await tools.run_tools(...)` **6,418 ms**（三步分别 6,415 / 6,414 / 6,417 ms，完全重叠），与 standard 的 6,284 ms 基本一致。
## 三、什么时候不该用

按形状选工具，别让一种工具做所有事：

| 形状 | 用什么 | 为什么 |
| --- | --- | --- |
| 互不依赖的多个动作 | 一次 `run_tools`（默认并发） | 省往返，工具侧并发 |
| 线性链 / 菱形汇合（先后能提前写死） | `run_tools` + `after`（下标或 label） | 依赖能静态表达，不必写程序 |
| 循环、条件分支、对前一步输出做计算/筛选 | `run_code` | `after` 只排顺序，不做数据流与控制流 |
| PTC 模式（顶层只有 `run_code`） | 程序里 `await tools.run_tools({steps:[...]})`；互不依赖的用 `Promise.all` | 保留程序表达力，别把独立动作写成串行 `await` |


- **有依赖关系**：B 需要 A 的产物时，用 `after: [0]` 或 `after: "build"`（前一步的 label）声明，别硬塞进同一个并发波次。
- **必须看结果才知道下一步**（浏览器点一下看一眼、逐步调试）：合批没有收益，收益本来就为零。
- **只有一个动作**：直接调用原工具，包一层只会多一次参数序列化。
- **单步会超过 `stepTimeoutMs`**（默认 60s）：要么调大，要么放后台。

从插件市场装（DSH 里添加索引 `https://raw.githubusercontent.com/66-zhimeng/dsh-plugins/main/market/index.json`，搜 `Dispatch`），或手工装：

```powershell
Copy-Item "D:\work\aigc-media\modules\dsh-dispatch" "$env:USERPROFILE\.dsh\profiles\web\node_modules\dsh-dispatch" -Recurse
```

```yaml
# ~/.dsh/profiles/<profile>/cordis.patch.yml
- insert:
    - id: tool-dispatch          # 换代码时必须改这个 id
      name: dsh-dispatch
      config:
        telemetryPath: C:\Users\<you>\.dsh\dsh-dispatch\telemetry.jsonl
```

保存即热挂载，**不需要重启**。

## 五、用法

```jsonc
{
  "steps": [
    { "tool": "pwsh", "arguments": { "command": "pnpm build" } },
    { "tool": "read", "arguments": { "file_path": "dist/index.js" }, "after": [0] },
    { "tool": "grep", "arguments": { "pattern": "TODO", "path": "src" } }
  ]
}
```

第 1、3 步同时跑，第 2 步等第 1 步完成。

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `steps[].after` | — | 数字/字符串或数组（下标或前序 label），指向更早的步；声明了才等待 |
| `maxParallel` | 8 | 同时最多几个步骤在飞 |
| `stopOnError` | true | 失败后不再启动新步骤（已在飞的不打断） |
| `stepTimeoutMs` | 60000 | 单步超时 |
| `totalTimeoutMs` | 180000 | 整批超时 |
| `perStepChars` | 800 | 每步结果回给模型的字符上限 |
| `exitCodeIsError` | true | 文本里出现非零 `[exit code: N]` 时判失败 |

`run_parallel`：`tasks: [{description, prompt}]`，最多 8 个，`maxParallel` 默认 8。

## 六、限制

- 只减少**往返次数**，不减少工具本身的耗时；单个慢工具（例如 60s 的构建）不会因为合批变快。
- 并发上限受模型侧影响：一次派太多次，上游可能排队（实测 8 路子 agent 中有一个首字等了 34.8s，是上游延迟不是插件排队）。
- 加速不是自动的：模型得真的把多个动作塞进一次 `run_tools`。一次只发一个调用时，和没有这个插件完全一样。
- 只作用于**本 profile** 的会话。
