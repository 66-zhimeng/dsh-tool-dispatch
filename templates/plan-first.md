# plan-first：一次规划多步

> 给模型看的模板。目的不是「少说话」，而是**把决策一次做完**，把动作压进一次往返。
> 每个往返的固定成本（实测 TTFT p50 ≈ 3.0s、整步 p50 ≈ 5.7s）与动作数量无关，只与往返次数成正比。

## 何时用

任务里出现「先看 A，再看 B，然后改 C」这类**可预知**的序列时——不是真需要看结果才能决定下一步，只是习惯性地一步一步来。

## 模板

```
目标：<一句话验收标准>
已知：<路径/命令/接口>
待确认：<真的必须先看结果才能决定的事，通常 0–1 件>

步骤（一次性下发）：
1. read  a.js
2. grep  "TODO"  src/
3. read  b.js
4. 汇总：这三处是否互相引用

只有第 4 步的结论可能改变后续时，才另起一步。
```

## 落地成调用

有 `run_tools` 时，上面的 1–3 步就是一次调用：

```json
{
  "steps": [
    { "tool": "read", "arguments": { "file_path": "a.js" } },
    { "tool": "grep", "arguments": { "pattern": "TODO", "path": "src/" } },
    { "tool": "read", "arguments": { "file_path": "b.js" } }
  ]
}
```

没有 `run_tools` 时，也可以在一条消息里发多个调用：它们共享同一次往返（虽然独占工具仍串行执行），这是零成本的第一步优化。

## 反例（不要这样）

```
read a.js        → 等
read b.js        → 等
grep TODO        → 等
summarize        → 等
```

四次往返、四次思考，做的事和上面一次调用完全相同。

## 判断标准

问自己一句：**「如果我现在就知道后面三步是什么，能不能一起发出去？」** 能——就一起发。
只有「下一步取决于这一步的结果」才是真串行。
